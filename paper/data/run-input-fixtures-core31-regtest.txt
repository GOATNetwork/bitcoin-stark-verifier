Scope
-----

This record covers the transaction-bound adaptor-signature and safe
Antichain-Winternitz input-publication fixtures.  Each run created the ordered
funding outputs, rebound the exported transactions to the real funding txid,
decoded representative full and tail transactions, and submitted every reveal
to Bitcoin Core's strict standard-policy mempool.  Raw transaction arguments
were passed to bitcoin-cli through stdin.  Repeated adaptor output scripts were
preserved in their exact order with bitcoin-tx because createrawtransaction
rejects duplicate address keys.

The reveal totals below include signatures, payload/opening witness items,
complete tapscripts, Taproot control blocks, input outpoints/scriptSig/sequence,
witness CompactSize framing, transaction globals and two serialized P2TR
outputs.  They are not payload-only estimates.  Funding is stated separately.
The adaptor and ACW fixtures do not yet export a common completion/finalization
transaction, timeout branches, anchors or the complete dispute graph.

BIP342 OP_CODESEPARATOR regression
----------------------------------

The first strict-Core adaptor attempt is preserved at:

  /mnt_zkm/stephen/input-adaptor-core31-regtest.h79yvV

After the funding transaction confirmed, Core rejected the first full reveal
with:

  mempool-script-verify-flag-failed (Invalid Schnorr signature)

The old adaptor fixture used the byte offset 32+3*i for the last executed
OP_CODESEPARATOR.  The pinned bitvm_scriptexec revision also records byte
offsets, so its transaction-aware execution reproduced the same error and gave
a false positive.  BIP342 defines codesep_pos as an opcode position; a
multi-byte data push counts as one opcode.  The repaired values are 0xffffffff
for the first signature and 3*i for signature index i>=1.  The repaired fixture
checks every signature directly with secp256k1 over the exact BIP341/BIP342
sighash, while the Core run independently executes the complete tapscript.

Signature, script, control-block and transaction-shell accounting
-----------------------------------------------------------------

Adaptor-signature fixture:

  * One 64-byte completed SIGHASH_DEFAULT Schnorr signature carries each
    eight-bit digit and binds the complete transaction.  There is no separate
    per-input authorization signature.
  * For d digits, the tapscript is 3*d+31 bytes and the witness has d+2 items:
    d signatures, the tapscript and a 33-byte depth-zero control block.
    A d=998 input therefore has a 3025-byte script and 1000 witness items.
  * Every reveal is a version-2 transaction with complete input shells and two
    43-byte P2TR TxOuts.  Marker/flag, counts, locktime and CompactSize lengths
    are included in the measured weight.

Safe ACW(2,16) fixture:

  * Every four-bit digit publishes two 20-byte chain values and one one-byte
    nonzero ScriptNum coordinate for canonical codeword [8,7].  Every P2TR
    input additionally carries one 64-byte SIGHASH_DEFAULT authorization
    signature that binds the transaction.
  * For d digits, the tapscript is 137*d+35 bytes and the witness has 3*d+3
    items: 3*d opening items, the authorization signature, tapscript and
    33-byte depth-zero control block.  A d=332 input has a 45519-byte script
    and 999 witness items; the d=300 tail input has a 41135-byte script and
    903 witness items.
  * Every reveal includes complete version-2 input shells and two 43-byte P2TR
    TxOuts.  The 11848875-vB result is the all-nonzero worst case; zero posted
    coordinates can reduce witness weight as documented in
    run-antichain-tx-cost.txt.

Signed Lamport fixture (for the same accounting boundary):

  * Every authenticated bit publishes one 16-byte preimage.  Every P2TR input
    also carries one 64-byte SIGHASH_DEFAULT authorization signature.
  * For d bits, the tapscript is 49*d+35 bytes and the witness has d+3 items:
    d preimages, authorization signature, tapscript and a 33-byte depth-zero
    control block.  A d=998 input has a 48937-byte script and 1001 witness
    items; script and control are removed before execution, leaving 999 initial
    stack items and a measured transient peak of 1000.
  * Each reveal includes complete version-2 input shells and one P2TR output.
    Its 174 reveals total 17265635 vB.  Unlike the adaptor and ACW fixtures,
    the Lamport fixture also serializes a signed 174-input finalization of
    13060 vB.  With its 45016-vB funding transaction, the Core-tested bounded
    subgraph is 17323711 vB; see run-lamport-core31-regtest.txt.

Interpretation limits
---------------------

These runs establish staged standard-policy acceptance on a disconnected
Bitcoin Core 31.1 regtest node.  They do not establish zero-confirmation
package acceptance: both funding-to-reveal edges were too large while the
funding parent was unconfirmed.  They also do not test public-P2P propagation,
fee-market robustness, reorg handling, timeout/challenge branches, anchors,
multi-copy soldering or the complete protocol graph.
